# Cardomancer API documentation

The HTTP API is documented as a live OpenAPI 3.1 spec, generated by
introspecting the running Flask app.

## Browsing the docs

Two entry points are available on a running Cardomancer instance:

| URL                       | What                                          |
| ------------------------- | --------------------------------------------- |
| `/docs`                   | Swagger UI rendered against the live spec     |
| `/api/openapi.json`       | The raw OpenAPI JSON                          |

Both endpoints are re-generated on every request, so they always
reflect the routes registered in the running build — no risk of the
docs drifting from the code.

## Generating the spec offline

For CI artifacts or contract testing, regenerate the on-disk snapshot:

```bash
python -m tools.generate_openapi          # writes docs/openapi.json
python -m tools.generate_openapi --json   # legacy alias, same result
pip install pyyaml                        # optional, enables YAML output
python -m tools.generate_openapi          # now also writes docs/openapi.yaml
```

CLI flags:

- `--no-json` — skip the JSON output (default: write)
- `--no-yaml` — skip the YAML output (skipped automatically without PyYAML)
- `--out-dir <path>` — directory relative to repo root (default: `docs`)

## What the generator captures automatically

- Every `@app.route` from `web_server.py`.
- Path parameters with their Flask converter type translated to
  OpenAPI primitives (`<int:n>` → `{n}` with `type: integer`).
- HTTP methods declared on each route.
- A summary + description pulled from the view function's docstring.
- A tag derived from the URL prefix (`/api/sort/configs` → tag `sort`).
- A default `403 csrf_failed` response on every state-changing method,
  mapped to the centralized `CSRFFailed` response component.

## What needs manual annotation

Request/response schemas. The view functions don't carry decorator
schemas, so the generator emits a generic `GenericObject` for both
sides. Hand-edit the precise schemas in `docs/openapi-overlay.yaml`
(not yet created — that's the extension point).

The auto skeleton is *complete* and *useful*: it gives an integrator a
full list of endpoints, methods, path params, and tag groupings. It's
not yet *precise* about every payload shape.

## Updating after adding a new endpoint

Nothing — the next request to `/api/openapi.json` (or `python -m
tools.generate_openapi`) picks it up automatically. The
`tests/test_openapi.py::BuildSpecTests::test_every_url_map_rule_appears`
test fails if a route slips through.

## Adding a precise schema to one endpoint

Hand-annotated schemas live in `docs/openapi-overlay.json`. The
generator deep-merges that file on top of the auto-generated
skeleton before writing `openapi.json` and before serving
`/api/openapi.json` live. Only fields you want to override or add
need to be present — everything else falls through from the
generator.

Example: give `/api/sort/start` a precise request body schema.

```json
{
  "components": {
    "schemas": {
      "SortStartRequest": {
        "type": "object",
        "required": ["preset"],
        "properties": {
          "preset": {
            "type": "string",
            "description": "Filename of the sort preset to use."
          },
          "continuous": { "type": "boolean", "default": false }
        }
      }
    }
  },
  "paths": {
    "/api/sort/start": {
      "post": {
        "requestBody": {
          "required": true,
          "content": {
            "application/json": {
              "schema": { "$ref": "#/components/schemas/SortStartRequest" }
            }
          }
        }
      }
    }
  }
}
```

The current overlay ships precise schemas for 14 load-bearing
endpoints — worker status, session lifecycle, sort presets list,
collection stats + filter, enrichment sources + refresh, database
status / refresh-prices / full-update, and calibration status.
Extend it when a new integrator surfaces.

### Merge semantics

- Dict values are merged key-by-key (recursive).
- Leaf values from the overlay overwrite the base.
- Lists are replaced wholesale (not concatenated). OpenAPI list
  fields like `tags` on an operation are curated sets, not
  append-lists.

The merge helper is unit-tested at
`tests/test_openapi.py::OverlayMergeTests`.
